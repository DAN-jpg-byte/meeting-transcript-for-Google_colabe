## 本文

# 長時間音声を「文字起こし＋話者分離」する仕組みについて考えたこと
今回考えたのは、2時間半〜4時間くらいある長い音声データを、Google Colabを使って安定して文字起こしし、さらに「誰が話したのか」まで分かる形に整理する方法。
最初は、Whisperで文字起こしした文章をLLMに渡して、「この文章はAさん、この文章はBさん」と文脈から判断してもらう方法を考えていた。しかし調べていくと、そもそも音声そのものから「この区間とこの区間は同じ人が話している」ということを判定する話者分離（Speaker Diarization）という技術があることが分かった。
そのため、基本的な処理はLLMに頼らなくてもかなりのところまで自動化できそう。
## 今回作りたいもの
元になるのは、2時間半、3時間、4時間といったかなり長い音声ファイル。
最終的には、例えば次のような形にしたい。
`plain text
00:12:03 - 00:12:08
話者A：
今日はこの件について話したいと思います。

00:12:09 - 00:12:14
話者B：
なるほど。前回の話ともつながっていますね。

00:12:15 - 00:12:22
話者A：
そうなんですよ。前回話した内容をもう一度整理すると……
`
つまり、「何を話したのか」と「誰が話したのか」の2つを組み合わせた会話記録を作る。
ここで重要なのは、この2つを最初から一つのAIに全部やらせなくてもいいということ。
## 処理を大きく2つに分ける
### ① Whisperによる文字起こし
Whisperには、「この時間帯では何が話されていたか」を判定してもらう。
例えば、
`plain text
00:20:13.2 → 00:20:18.5
「昨日ちょっと調べてみたんだけど」
`
というデータを作る。
Whisper側では、誰が話しているかまでは無理に判断しなくていい。
### ② 話者分離
もう一方では、音声を話者分離用のAIに処理させる。
こちらは文章の内容ではなく、主に「声」を見て、
`plain text
00:20:10 → 00:20:16
SPEAKER_00

00:20:16 → 00:20:24
SPEAKER_01
`
のような結果を作る。
つまり、
- Whisper → 何を言ったのか
- 話者分離 → 誰が言ったのか
という役割分担になる。
話者分離も中ではAI・機械学習を使っているが、ChatGPTやGeminiのような巨大なLLMとは違い、「声を区別する」という特定の仕事に特化したモデルなので、Colabなどでも比較的扱いやすい。
# 長時間音声は最初にチャンクへ分ける
今回特に重要なのがここ。
4時間の音声をそのまま一気にWhisperに入れると、処理時間が非常に長くなる。
さらにGoogle Colabの場合、
- セッションが途中で切れる
- GPUが落ちる
- Whisperの処理でエラーになる
- ブラウザ側の接続が切れる
などが起きる可能性がある。
4時間処理して、3時間50分のところで落ちて全部やり直し、という状態は避けたい。
そこで、最初に音声を小さなチャンクへ分割しておく。
## Whisperは10分程度のチャンク
文字起こしについては、今考えているように10分単位くらいがかなり扱いやすそう。
4時間なら、
`plain text
chunk_000  00:00:00〜00:10:00
chunk_001  00:10:00〜00:20:00
chunk_002  00:20:00〜00:30:00
...
chunk_023  03:50:00〜04:00:00
`
という24個のファイルになる。
それぞれ処理が完了するたびに結果を保存する。
例えば、
`plain text
transcript_000.json
transcript_001.json
transcript_002.json
`
などとして残しておく。
そうすると、仮に17番目の処理中にColabが落ちても、
`plain text
0〜16 → 完了済み
17〜 → 再開
`
とできる。
これなら、長時間音声でもかなり安心して処理できる。
# 話者分離もチャンク化する
話者分離についても、4時間を一気に処理するより、ある程度チャンクに分けた方が安全。
ただし、Whisperとまったく同じ10分にする必要はない。
現時点では例えば、
Whisper：10分
話者分離：30分前後
くらいから試してみるのがよさそう。
例えば、
`plain text
Diarization 01
00:00〜00:30

Diarization 02
00:30〜01:00

Diarization 03
01:00〜01:30
`
という形。
Whisperより大きめにする理由は、話者分離ではある程度長い時間の中で声を比較した方が、「この声とこの声は同じ人」という情報を持ちやすいから。
# ただし話者分離のチャンクには問題がある
ここが今回かなり重要なポイント。
話者分離モデルが、
`plain text
SPEAKER_00
SPEAKER_01
`
と名前をつけたとしても、この番号には本当の意味での人物情報は入っていない。
例えば最初の30分で、
`plain text
SPEAKER_00 = 自分
SPEAKER_01 = 田中さん
`
となったとしても、次の30分では、
`plain text
SPEAKER_00 = 田中さん
SPEAKER_01 = 自分
`
となる可能性がある。
つまり、チャンクごとに番号が振り直される可能性がある。
そのため、SPEAKER_00だから全部同じ人、とは限らない。
# そこで「オーバーラップ」を使う
この問題への対策として、話者分離用の音声チャンクを完全に30分ずつ切るのではなく、少し重ねる方法が使えそう。
例えば、
`plain text
チャンク1
00:00〜30:00

チャンク2
29:00〜59:00

チャンク3
58:00〜1:28:00
`
のように、1分程度重ねる。
すると、
`plain text
29:00〜30:00
`
はチャンク1とチャンク2の両方に入っている。
この部分で話している声を比較すれば、「チャンク1のSPEAKER_00と、チャンク2のSPEAKER_01は同じ人物だ」という対応関係を作れる可能性がある。
つまり、オーバーラップ部分を話者IDをつなぐための「のりしろ」として使う。
この方法なら、30分単位で安全に処理しながら、4時間全体として同じ人物のIDをなるべく統一できる。
# 一番大事なのは「元音声の時間」を保存すること
Whisperと話者分離を別々に処理しても、最後に合体できる。
そのために重要なのがタイムスタンプ。
例えば10分目から20分目のWhisperチャンクの中で、
`plain text
00:02:15
`
という結果が出た場合、これはチャンク内では2分15秒だが、元の4時間音声では、
`plain text
00:12:15
`
になる。
つまり、
`plain text
元音声上の時間
=
チャンク開始時間
+
チャンク内の時間
`
として保存しておく。
これをWhisperにも話者分離にも行う。
そうすると、両方が同じ「元音声の00:00:00から何秒後か」という共通の時間軸を持てる。
ここはかなり重要。
# 最後の突き合わせ処理は軽い
4時間分の文字起こしと4時間分の話者分離結果を最後に合体させる、と聞くと非常に重そうに感じる。
しかし実際には、この部分はそれほど重くない。
例えば、
`plain text
Whisper

開始 721秒
終了 726秒
文章「昨日調べてみたんだけど」
`
というデータがあり、
`plain text
話者分離

開始 719秒
終了 728秒
SPEAKER_01
`
というデータがあれば、
`plain text
721〜726秒はSPEAKER_01の区間と重なっている
`
とPythonで判定するだけ。
したがって、
`plain text
00:12:01〜00:12:06
SPEAKER_01
「昨日調べてみたんだけど」
`
と結合できる。
これはLLMを使う必要も、GPUを使う必要もなく、普通のPython処理でできる。
4時間分程度であれば、基本的にはまとめて処理して問題なさそう。
重い処理は音声をAIに解析させる部分。
最後のデータ結合は軽い処理。
と考えると分かりやすい。
# 全体の流れ
現時点で考えている構成をまとめると、こんな形になる。
`plain text
元音声
2.5〜4時間
        ↓
音声をチャンクに分割
        ↓
 ┌──────────────┬──────────────┐
 │                              │
 │ Whisper                      │ 話者分離
 │ 10分程度                     │ 30分程度
 │                              │ 少しオーバーラップ
 ↓                              ↓
文字起こし結果                  話者情報
＋タイムスタンプ                ＋タイムスタンプ
 │                              │
 └──────────────┬──────────────┘
                ↓
       Pythonで時間を照合
                ↓
      発言 ＋ 話者を結合
                ↓
SPEAKER_00：「……」
SPEAKER_01：「……」
                ↓
      必要なら人物名へ変換
                ↓
        LLMで文章を整える
`
かなり整理された構成になりそう。
# 話者名は後から付ければいい
話者分離の時点では、
`plain text
SPEAKER_00
SPEAKER_01
SPEAKER_02
`
くらいで十分。
最初からSPEAKER_00が誰なのかまでAIに当てさせる必要はない。
一度結果を見て、
`plain text
SPEAKER_00 → 自分
SPEAKER_01 → Aさん
SPEAKER_02 → Bさん
`
という対応表を人間が指定すればいい。
あとはプログラムで一括置換できる。
その方がシンプルだし、名前をAIが勝手に推測する必要もない。
# LLMは「最後の仕上げ」だけでよさそう
当初はGeminiやGroqなどのLLMを使って、誰が話したのかまで判断させることも考えていた。
しかし、今回の仕組みなら主要部分ではLLMをほとんど使わなくてもよさそう。
LLMが役に立ちそうなのは最後。
例えば音声の文字起こしは、そのままだと、
`plain text
えーと、だからその、なんていうのかな、
まあその、この前のやつが、あれで……
`
のような非常に口語的な文章になる。
そこでLLMには、発言の意味を変えずに、読みやすい文章へ整えるという仕事をしてもらう。
また、SPEAKER_00とSPEAKER_01の判定が一部おかしくなっているところについて、前後の会話から「この一文だけ話者が逆ではないか」と文脈で補正してもらう使い方も考えられる。
つまりLLMは、文字起こしの中心処理ではなく、「校正・補正担当」にする。
これならGeminiやGroqなどの無料API枠でもかなり足りる可能性が高い。
# この構成の良いところ
今回の構成で特に良いのは、途中で処理が止まっても最初からやり直さなくていいこと。
長い音声を一つの巨大な処理として扱うのではなく、
`plain text
音声分割
↓
1チャンク処理
↓
結果保存
↓
次のチャンク
`
という方式にする。
さらに、
`plain text
ファイルがすでに存在する
→ 処理済みなのでスキップ

ファイルが存在しない
→ そこから処理
`
という仕組みにしておけば、Colabが落ちても簡単に続きから再開できる。
4時間の音声でも、一度処理した部分を何度も計算し直す必要がない。
# 今のところ考えている基本方針
まずは次の設定から試してみる。
- 元音声：2.5〜4時間程度
- Whisper：10分チャンク
- 話者分離：30分程度のチャンク
- 話者分離チャンク：境界を少しオーバーラップ
- すべての結果：元音声基準のタイムスタンプを保存
- 処理結果：1チャンクごとに保存
- 途中から再開可能にする
- 最後：Pythonで文字起こしと話者情報を一括結合
- 人物名：人間がSPEAKER番号との対応を一度指定
- LLM：最後の文章整理・話者ミス補正だけに使用
という構成。
この方法なら、「重いAI処理は小分けにして安全に進め、軽いデータ処理は最後にまとめて行う」という形になる。
Google Colabのように途中でセッションが切れる可能性がある環境とも相性がよさそう。
また、LLMへの依存をかなり減らせるので、GeminiやGroqの無料API枠を大量に消費する必要もなくなる。
最終的には、音声を入れて処理を開始すれば、途中保存しながら文字起こしと話者分離が進み、最後に「誰が・いつ・何を話したか」がまとまったデータが完成する仕組みを目指す。
